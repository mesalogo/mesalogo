# Alembic migrations (backend-fastapi)

> This is the canonical schema-management tool for the FastAPI backend.
> Any change under `app/models.py` MUST be accompanied by an Alembic
> revision in this directory. See `AGENTS.md §3.2` (red lines).

The legacy `backend-fastapi/migrations/` directory is **historical only**
(hand-written SQLite scripts from the LightRAG feature). Do not add new
migrations there.

---

## Quickstart

### Fresh empty database

```bash
# 1. Create an empty MariaDB / MySQL schema with utf8mb4
mysql -u <user> -p -e "CREATE DATABASE abm CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 2. Configure backend-fastapi/config.conf → DATABASE_URI

# 3. Just start the service. Migration is automatic.
cd backend-fastapi
python run_app.py
```

That's it. On startup `init_database()` runs the equivalent of
`alembic upgrade head` itself, then seeds initial data, then loads
system settings.

### Database that was created by an older startup (no `alembic_version`)

Nothing to do. The auto-migrator detects this case and calls
`alembic stamp head` followed by `alembic upgrade head` on the first
boot, adopting the existing schema as baseline.

### Bypassing the auto-migrator

There is exactly one documented bypass, intended for environments where
a separate operator step runs migrations (for example, a CI step before
the service container starts):

```bash
ABM_SKIP_DB_MIGRATE=1 python run_app.py
```

When this is set, the service will start even if the DB schema is
behind the code. ORM queries that hit missing columns/tables will fail
at runtime. **Do not** set this in development.

### Manual operations (rare)

```bash
conda run -n abm alembic current       # what revision is the DB on
conda run -n abm alembic history       # full revision graph
conda run -n abm alembic upgrade head  # same as auto-migrate
conda run -n abm alembic downgrade -1  # roll back one revision
```

## Day-to-day workflow

### Change a model

1. Edit `app/models.py`. Keep the change small.
2. Generate a revision:

   ```bash
   conda run -n abm alembic revision --autogenerate -m "short imperative summary"
   ```
3. **Open the new file under `alembic/versions/` and review.**
   `--autogenerate` is best-effort: it sometimes hallucinates type
   changes (e.g. `String(N)` vs `VARCHAR(N)` with a different collation,
   or `JSON` vs `LONGTEXT`). Delete the noise; keep only the real diff.
4. Make sure `downgrade()` is the exact inverse of `upgrade()`. If the
   autogenerated downgrade uses `None` for constraint names, replace
   them with explicit names so the inverse is deterministic.
5. Run the upgrade locally:

   ```bash
   conda run -n abm alembic upgrade head
   ```
6. Test downgrade locally too (cheapest insurance):

   ```bash
   conda run -n abm alembic downgrade -1
   conda run -n abm alembic upgrade head
   ```
7. Commit `alembic/versions/<file>.py` together with the `models.py`
   change in the same commit.

### Inspect state

```bash
conda run -n abm alembic current       # which revision the DB is on
conda run -n abm alembic history       # all revisions
conda run -n abm alembic heads         # latest revision(s)
```

### Generate SQL without running it (review before applying to prod)

```bash
conda run -n abm alembic upgrade <from_rev>:<to_rev> --sql > upgrade.sql
```

## Gotchas / lessons learned

- **Running `alembic upgrade head` against a DB that has live
  connections (e.g. `uvicorn` running) may hang on `ALTER TABLE` waiting
  for the metadata lock.** Stop the service first, or accept that
  `lock_wait_timeout` will eventually fail the migration.
- **`init_database()` (called on every service startup) still runs
  `Base.metadata.create_all()`**, which is idempotent (only creates
  missing tables). It does NOT bypass Alembic for existing tables, so
  it's safe to keep — but never rely on `create_all()` to add columns
  or change constraints. Always go through Alembic for that.
- **`env.py` reads the URL from `core.config.settings.DATABASE_URI`**,
  NOT from `alembic.ini`. Never put real credentials in `alembic.ini`.
- **Constraint names matter.** MariaDB autogenerates names like
  `conversations_ibfk_1` if you don't specify; this makes downgrades
  brittle. When you add a FK in a migration, pass an explicit name.

## Why was this added in 2026-05?

Two parallel bugs on the action-task mainline:

1. `POST /api/action-tasks` returned 500 because the route handler
   directly called another route handler with `Depends(...)` defaults
   that never resolved.
2. `DELETE /api/action-tasks/{id}` without `?cascade=true` returned 500
   because `Conversation.action_task_id` was NOT NULL but SQLAlchemy's
   default cascade tried to set it to NULL.

Bug 2 needed a real schema change (`ON DELETE CASCADE` on the FK), and
the codebase didn't actually have Alembic installed despite
`AGENTS.md` claiming so. Setting it up was a prerequisite to fixing the
bug properly. See
`docs/agents/failures/2026-05-18-action-task-delete-cascade-default.md`
for the full incident write-up.
